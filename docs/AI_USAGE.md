## 1. How I used AI during the task

I used **Claude Code** (Anthropic, Claude Opus 5.5) inside VS Code as a pair programmer with access to
the project folder and terminal.

1. **Discussing the task.** I discussed the task requirements with the assistant before starting.
2. **Environment setup.** It gave me the install commands for my machine. It diagnosed a Windows-specific failure
   (`cmd.exe` strips the `^` in Composer version constraints) and found that FlyEnv's PHP comes before Laragon's in PATH.
3. **Matching the required stack.** I checked the project against the brief's tech stack: **Laravel 11 + Livewire v3 +
   Alpine.js + Filament v3 + Pest + MySQL** (+ Docker). While setting it up, we found that every Laravel 11 release carries
   unpatched security advisories (Laravel 11 is end-of-life). I chose to follow the brief exactly, ignore only those specific
   advisory IDs, and document the risk (README › Security note).
4. **Implementation.** The assistant wrote the schema, services, mock provider, tests, Filament screen, seeders and docs.
   It ran the test suite after each step.
5. **Verification.** Tests run after every step, on SQLite and on real MySQL, plus an end-to-end login and page check in Docker.
   Bugs they caught and that were fixed:
   * `PayoutService::reconcile()` decided based on a stale in-memory `Payout` instead of the current database row,
     so it re-queued a payout that should have been failed.
   * `Money::allocate()` accepted negative weights when they summed to zero (e.g. `[1, -1]`). The validation now runs first.
   * In Docker, `php artisan serve` doesn't forward container environment variables to its workers, so web requests
     couldn't reach MySQL. The entrypoint now writes them into `.env`.

## 5. What differentiates this solution

* **Money is provably conserved.** Balances are derived from an append-only ledger, never stored. A randomised test
  runs many payouts against a randomly failing provider and checks, for every instructor, that
  *earned = owed + actually transferred*.
* **A timeout is treated as "unknown", not "failed".** Retries reuse the idempotency key, and reconciliation asks the provider.
  Even a straggling request that lands after we gave up is handled (`failed → succeeded` re-debits).
* **One state machine** for API responses, webhooks and reconciliation, with protection against stale, out-of-order events.
* **Refunds distinguish unearned from earned money.** Instructors are only clawed back for what they were actually allocated,
  and the partially used month is settled fairly by viewing.
* **The Senior Bonus reuses existing mechanics.** A plan change is a refund-to-credit, so no new money logic is needed.

## 6. Trade-offs, architectural decisions and improvements chosen on purpose

* Single-entry ledger with a platform account instead of full double-entry: enough to prove conservation, and much simpler to review.
* `SUM()` balances instead of stored balances: always correct. A projection is the scaling path.
* Monthly recognition instead of daily proration: simpler to explain to instructors.
* Webhooks processed synchronously: fine at this scale. Queue them at volume.
